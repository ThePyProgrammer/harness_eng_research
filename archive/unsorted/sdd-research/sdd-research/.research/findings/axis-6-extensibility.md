# Axis 6: Extensibility, Modularity & Platform Integration

## Question
How customizable and extensible are these tools — what plugin systems, hooks, MCP integrations, and configuration options do they offer, and how do they integrate with different platforms?

## Narrative Analysis

### 1. Architectural Patterns: Three Distinct Paradigms

The spec-driven tooling landscape has crystallized into three architectural paradigms, each with different extensibility trade-offs.

**CLI-First Modular Tools** (OpenSpec, GitHub Spec Kit, Lean Spec, AI Factory, SpecPulse, cc-sdd) distribute as installable CLI packages that scaffold project directories with configuration files, templates, and slash commands. These tools prioritize cross-platform compatibility, typically supporting 8-20+ AI agents through a unified command interface. OpenSpec is the most extensible in this category, offering a full custom schema system where teams can define entirely new artifact types and workflow sequences in `openspec/schemas/` directories with `schema.yaml` definitions and corresponding Markdown templates [OpenSpec Custom Schemas](https://intent-driven.dev/blog/2026/02/12/openspec-custom-schemas/). GitHub Spec Kit similarly emphasizes openness, supporting a generic agent mode (`--ai generic --ai-commands-dir`) and enabling domain-specific forks like IBM's Infrastructure-as-Code variant [Augment Code: 6 Best SDD Tools](https://www.augmentcode.com/tools/best-spec-driven-development-tools). AI Factory takes extensibility further with a full skill/extension framework supporting "commands, injections, MCP, agents" as installable units [AI Factory GitHub](https://github.com/lee-to/ai-factory). (Confidence: High)

**Deep Platform-Native Plugins** (Pilot Shell, Smart Ralph, PAUL, ContextKit, Tasker, Spec Kit Command Cursor) are purpose-built for a single platform -- most commonly Claude Code, with Spec Kit Command Cursor targeting Cursor IDE exclusively. These tools exploit platform-specific capabilities that cross-platform tools cannot access. Pilot Shell is the most sophisticated example, implementing a full lifecycle hook system (PostToolUse, SessionStart, PreToolUse, PreCompact, Stop, SessionEnd) with five integrated MCP servers providing library documentation lookup, persistent memory search, web search, GitHub code search, and web page fetching [Pilot Shell GitHub](https://github.com/maxritter/pilot-shell). Smart Ralph provides two independent plugin variants (ralph-specum and ralph-speckit) with execution-controlling hooks in a dedicated `hooks/` directory [Smart Ralph GitHub](https://github.com/tzachbon/smart-ralph). Spec Kit Command Cursor is remarkably deep for a Cursor-only tool, implementing six specialized subagents with DAG-based parallel execution, async background agents, and file conflict detection across parallel tasks [Spec Kit Command Cursor GitHub](https://github.com/madebyaris/spec-kit-command-cursor). (Confidence: High)

**MCP Server Implementations** (mcp-server-spec-driven-development, spec-workflow-mcp, openspec-mcp, Lean Spec's @leanspec/mcp) expose spec-driven workflows as Model Context Protocol services that any MCP-compatible client can consume. This is the most platform-agnostic approach -- any editor or agent supporting MCP can connect. The openspec-mcp server is the most feature-rich, exposing full context/analysis tools, management operations, quality assurance validation, workflow management, an approval state machine (draft -> pending_approval -> approved -> implementing -> completed -> archived), and a review system with comment threading and resolution tracking [OpenSpec MCP GitHub](https://github.com/Lumiaqian/openspec-mcp). The spec-workflow-mcp server adds a real-time web dashboard and a VSCode extension for monitoring project progress [Spec Workflow MCP GitHub](https://github.com/Pimzino/spec-workflow-mcp). By contrast, mcp-server-spec-driven-development offers a simpler three-prompt pipeline (requirements -> design -> code) with minimal customization [MCP Server SDD GitHub](https://github.com/formulahendry/mcp-server-spec-driven-development). (Confidence: High)

### 2. Hook Systems and Lifecycle Management

Hook sophistication varies dramatically across tools. Pilot Shell leads with the most granular hook system found in this analysis: PostToolUse hooks dispatch language-specific formatters and linters (ruff+basedpyright for Python, Prettier+ESLint+tsc for TypeScript, gofmt+golangci-lint for Go) after every file edit, while SessionStart hooks restore persistent context via memory loaders, and PreCompact hooks capture active plans before context window compaction [Pilot Shell GitHub](https://github.com/maxritter/pilot-shell). GSD implements session lifecycle hooks for statusline updates, context monitoring, and session tracking, with the explicit goal of combating "context rot" by externalizing state into files and executing plans in fresh context windows [GSD GitHub](https://github.com/gsd-build/get-shit-done). PAUL takes a different approach with mandatory loop enforcement (PLAN -> APPLY -> UNIFY) and CARL (Context Augmentation & Reinforcement Layer), which dynamically loads rules based on what directory or file type the developer is working in [PAUL GitHub](https://github.com/ChristopherKahler/paul). Spec Kit Command Cursor implements hooks via `hooks.json` triggered by `subagentStop` and `stop` events, enabling workflow automation at agent boundaries [Spec Kit Command Cursor GitHub](https://github.com/madebyaris/spec-kit-command-cursor). Most other tools lack documented hook systems entirely. (Confidence: High)

### 3. MCP Integration Depth

MCP integration exists on a spectrum from native servers to casual references. Tools that implement their own MCP servers (openspec-mcp, spec-workflow-mcp, mcp-server-spec-driven-development, @leanspec/mcp) offer the deepest integration, exposing their full functionality as protocol-compliant tools that any MCP client can invoke. Pilot Shell integrates five third-party MCP servers configured in `.mcp.json` to augment its workflow with external capabilities [Pilot Shell GitHub](https://github.com/maxritter/pilot-shell). AI Factory auto-configures MCP servers during `ai-factory init` based on which AI agent the user selects [AI Factory GitHub](https://github.com/lee-to/ai-factory). Lean Spec provides a native `@leanspec/mcp` package installable via standard MCP configuration [Lean Spec GitHub](https://github.com/codervisor/lean-spec). Many tools (GitHub Spec Kit, Spec Kitty, Shotgun, SpecPulse) reference MCP Registry support in their documentation but provide no concrete implementation details. This gap may indicate future development or may reflect that their primary integration path is through slash commands rather than protocol-level interoperability. (Confidence: Medium -- many MCP references are vague)

### 4. Multi-Platform vs. Single-Platform Trade-offs

The cross-platform tools (OpenSpec with 20+ agents, GitHub Spec Kit with 20+ agents, cc-sdd with 8 agents, SpecPulse with 8 platforms, AI Factory with 14+ agents) achieve breadth by standardizing on the lowest common denominator: slash commands backed by Markdown templates and structured directory conventions. GSD pioneered a particularly interesting multi-runtime approach, merging conversion logic for Claude Code, OpenCode, Gemini CLI, and Codex into a single `npx get-shit-done-cc` installer while maintaining 11 specialized agents and a full set of workflow definitions [GSD Multi-Runtime Article](https://medium.com/@richardhightower/one-codebase-three-runtimes-how-gsd-targets-claude-code-opencode-and-gemini-cli-29c98cfe96c6). Spec Kitty supports 12 agents with dedicated command directories per agent (`.claude/commands/`, `.cursor/commands/`, `.gemini/commands/`), each receiving 13 auto-loaded slash commands [Spec Kitty GitHub](https://github.com/Priivacy-ai/spec-kitty). The single-platform tools sacrifice breadth for depth: Pilot Shell's five MCP servers, lifecycle hooks, language server integration (basedpyright, vtsls, gopls), and model routing strategy (Opus for planning, Sonnet for implementation) are only possible because it targets Claude Code exclusively [Pilot Shell GitHub](https://github.com/maxritter/pilot-shell). Similarly, Spec Kit Command Cursor's subagent trees, async background execution, and DAG-based parallel scheduling leverage Cursor-specific capabilities unavailable through generic slash commands [Spec Kit Command Cursor GitHub](https://github.com/madebyaris/spec-kit-command-cursor). Martin Fowler's analysis notes that GitHub Spec Kit is "the most customizable one of the three tools" when compared to Kiro and Tessl, largely because of its open template system and generic agent support [Martin Fowler SDD Tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html). (Confidence: High)

### 5. Template and Schema Customization

Template customization is the most universal extensibility mechanism across the ecosystem. Nearly every tool uses Markdown-based templates stored in project directories. The distinguishing factor is schema-level customization: OpenSpec allows defining entirely new artifact types and workflow sequences through custom `schema.yaml` files, where each artifact declares what it generates, which template to use, and what it requires before creation [OpenSpec Custom Schemas](https://intent-driven.dev/blog/2026/02/12/openspec-custom-schemas/). GitHub Spec Kit uses a "constitution" concept to establish project-level governance principles that all subsequent AI interactions must obey [Spec Kit GitHub](https://github.com/github/spec-kit). cc-sdd provides customizable templates and rules in `settings/` directories supporting "PRD-style requirements, API/database schemas, approval gates, JIRA integration, domain-specific standards" [cc-sdd GitHub](https://github.com/gotalab/cc-sdd). Smart Ralph takes a dual approach, offering both a flexible `ralph-specum` plugin and a `ralph-speckit` variant implementing GitHub's spec-kit methodology with constitution-first governance [Smart Ralph GitHub](https://github.com/tzachbon/smart-ralph). PAUL uses a unique CARL system for dynamic rule loading based on development context rather than static template selection [PAUL GitHub](https://github.com/ChristopherKahler/paul). (Confidence: High)

### 6. Orchestration and Multi-Agent Patterns

Several tools implement sophisticated multi-agent orchestration. GSD deploys 4 parallel researchers in the investigation phase, followed by a planner-checker loop for planning, parallel executors with independent 200k-token context windows per task, and dedicated verifiers and debuggers [GSD GitHub](https://github.com/gsd-build/get-shit-done). Spec Kit Command Cursor implements a full subagent tree architecture where orchestrators can spawn implementers that invoke verifiers, with support for truly parallel DAG execution across 20+ tasks using file conflict detection to prevent parallel edits to identical files [Spec Kit Command Cursor GitHub](https://github.com/madebyaris/spec-kit-command-cursor). Spec Kit Plus positions itself at the infrastructure level, integrating OpenAI Agents SDK, A2A (Agent-to-Agent) protocol, Kubernetes, Dapr, and Ray for production-grade distributed multi-agent systems [Spec Kit Plus GitHub](https://github.com/panaversity/spec-kit-plus). Spec Kitty exposes an Orchestrator API that external orchestrators can call while respecting policy boundaries at the host API level [Spec Kitty GitHub](https://github.com/Priivacy-ai/spec-kitty). ContextKit takes the opposite approach, deliberately optimizing for individual developers rather than team simulation, arguing that the overhead of multi-agent team roles is unnecessary for solo work [ContextKit GitHub](https://github.com/FlineDev/ContextKit). (Confidence: High)

### 7. Dashboards and Visual Management

A subset of tools provides visual interfaces beyond the terminal. Spec Kitty offers a real-time kanban dashboard with four workflow lanes (planned -> doing -> for_review -> done), progress tracking, and multi-agent visibility showing which AI agent works on each task [Spec Kitty GitHub](https://github.com/Priivacy-ai/spec-kitty). The openspec-mcp server includes a web interface with an overview, kanban board, change listings, QA runner, project context analysis, specification browser, and approval queue management, all with real-time WebSocket updates [OpenSpec MCP GitHub](https://github.com/Lumiaqian/openspec-mcp). The spec-workflow-mcp server provides both a web dashboard (port 5000 by default, localhost-only) and a VSCode extension sidebar offering equivalent functionality [Spec Workflow MCP GitHub](https://github.com/Pimzino/spec-workflow-mcp). Most other tools remain terminal-only, relying on Markdown files and slash command output for status visibility. (Confidence: High)

## Key Unknowns

1. **OpenKit**: No tool by this exact name was found in the spec-driven development ecosystem despite multiple search attempts. It may be known by a different name, may be a private/internal tool, or may have been conflated with another project (possibly OpenSpec or GitHub Spec Kit).

2. **MCP Registry depth**: Many tools (GitHub Spec Kit, Spec Kitty, Shotgun, SpecPulse, GSD) reference "MCP Registry -- Integrate external tools" in their navigation/documentation but provide no concrete implementation details. It is unclear whether these are active integrations or planned features.

3. **Kiro's extensibility**: While Kiro (by Amazon) was mentioned in comparisons and implements Agent Hooks on file events, its extensibility is noted as more limited than spec-kit by Martin Fowler's analysis [Martin Fowler SDD Tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html). Its full hook API and plugin system remain under-documented in public sources.

4. **Tessl's MCP server**: Tessl's CLI reportedly doubles as an MCP server with bidirectional spec-code syncing [Martin Fowler SDD Tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), but detailed configuration and extensibility documentation was not found.

5. **Commercial vs. open-source feature gaps**: Shotgun is partially closed-source with paid workspace features; Intent (by Augment Code) has a proprietary Context Engine MCP. The full extensibility capabilities of commercial tools versus their open-source counterparts remain difficult to compare.

6. **PAUL and ContextKit hook performance**: Both tools describe context-aware dynamic rule loading (CARL for PAUL, auto-detection for ContextKit), but real-world performance impact and edge-case behavior are not documented.

7. **Inter-tool composability**: Whether tools like OpenSpec's MCP server can be used alongside GSD's multi-runtime system or Pilot Shell's hook architecture is not documented by any source. The ecosystem appears to assume exclusive tool adoption rather than composition.

8. **Conflicting information**: The Augment Code comparison article lists Intent as having a "dedicated Context Engine MCP for semantic understanding across 400,000+ files" [Augment Code: 6 Best SDD Tools](https://www.augmentcode.com/tools/best-spec-driven-development-tools), but Intent is Augment Code's own product, making this a self-promotional claim that could not be independently verified.
