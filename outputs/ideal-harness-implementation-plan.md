# Implementation Plan: The Ideal AI Coding Agent Harness

## Design Philosophy

This plan synthesizes three sources:
1. **The formal framework** (science.tex) -- 7 pillars, 35 design principles, cross-pillar constraints
2. **RAPID's execution architecture** -- sets, worktrees, DAG ordering, contracts, adversarial review, crash recovery
3. **Blueprint's governance architecture** -- ADR lifecycle, evidence tracking, drift detection, fitness functions, configurable governance tiers

Plus the three reviewer-identified gaps: **cost optimization**, **human-in-the-loop interaction**, and **model routing**.

The result is a 10-pillar harness architecture with concrete implementation guidance.

## Pillar 1: Specification & Context Engine

**Paper grounding:** Abstraction + Information pillars. Context Budget Theorem (optimal at 0.15W-0.40W). Fresh Context Dominance. Curation Beats Accumulation.

**RAPID inspiration:** Scoped CLAUDE.md per worktree, three-tier information architecture, SET-OVERVIEW.md generation.

### 1.1 Three-Tier Context Architecture

```
config/
  context/
    ACTIVE.md          # Always-loaded (< 80 lines). Project rules, conventions, deny-lists.
    ARCHITECTURE.md    # Generated by Blueprint cartographer agent. Module map + invariants.
    CONVENTIONS.md     # Naming, patterns, error handling conventions.
    
  searchable/
    index.json         # Structural index of codebase (function signatures, types, modules)
    reuse-map.json     # The "reuse map" from Information pillar: (name, signature, location)
    dependency-graph/  # AST-extracted import/export graph for structural navigation
    
  hidden/
    .gitignore-like    # Binary files, generated code, secrets -- structurally excluded
```

**Implementation:**

| Component | What It Does | Token Budget |
|-----------|-------------|--------------|
| Active tier | Always in context. Project rules, CLAUDE.md, architecture overview. | 5-15% of W |
| Searchable tier | On-demand retrieval via grep/glob/semantic. Reuse map, dependency graph. | Unbounded store, retrieval consumes active budget |
| Hidden tier | Structurally excluded. .gitignore-like enforcement. | 0 (never loaded) |

**Key implementation detail:** The reuse map (from the paper's Information pillar, Section 3.8) is the highest-leverage active-tier item. It compresses the codebase for reuse decisions at ~1000x compression ratio:

```json
// reuse-map.json -- auto-generated, refreshed on file change
{
  "functions": [
    {"name": "authenticate", "sig": "(user: string, pass: string) => Promise<Token>", "loc": "src/auth/index.ts:42"},
    {"name": "validateInput", "sig": "(schema: ZodSchema, data: unknown) => Result", "loc": "src/utils/validation.ts:15"}
  ],
  "types": [
    {"name": "User", "loc": "src/types/user.ts:3", "fields": ["id", "email", "role"]},
    {"name": "ApiResponse<T>", "loc": "src/types/api.ts:1", "fields": ["data", "error", "status"]}
  ]
}
```

### 1.2 Scoped Context Generation (from RAPID)

When a task begins, generate a scoped context document:

```markdown
# Task Context: {task-description}

## Project Overview
{First 30 lines of ACTIVE.md}

## Relevant Files (structural navigation, not semantic search)
{Dependency-graph traversal from target files, 1-2 hops}

## Reuse Candidates
{Reuse map entries relevant to this task}

## File Ownership (if multi-agent)
MODIFY: {owned files}
READ ONLY: {interface files from other agents}
DO NOT TOUCH: {deny list}

## Active Contracts
{CONTRACT.json interfaces this task must preserve}
```

**Token budget enforcement:** The context generator stops adding items when the marginal inclusion bar is exceeded (paper Theorem 3.3: marginal value must exceed `[delta(|C|+|Delta|) - delta(|C|)] / [1-delta(|C|+|Delta|)] * V_eff(C)`).

### 1.3 Positional Ordering

From the paper's U-shaped recall function: place highest-relevance items at context boundaries (beginning and end), lowest-relevance in the middle. Concretely:

```
[BEGINNING -- high relevance]
  1. Task specification
  2. Active contracts / interfaces
  3. File ownership + deny list
  
[MIDDLE -- lower relevance]
  4. Architecture overview
  5. Convention guide
  6. Dependency context
  
[END -- high relevance]
  7. Reuse map (what already exists)
  8. Recent changes (git diff of relevant files)
  9. Explicit instructions / constraints
```

### 1.4 Fresh Context Protocol

From the paper's Fresh Context Dominance proposition and RAPID's execution model:

- **Every agent invocation gets fresh context.** No accumulated conversation state.
- **Checkpoint at 35 minutes or 50K tokens** -- whichever comes first. Save HANDOFF.md, restart with curated summary.
- **RAPID pattern:** After /clear, the harness is fully self-contained from disk artifacts (STATE.json, PLAN.md, WAVE-COMPLETE.md markers).

## Pillar 2: Task Decomposition & Planning

**Paper grounding:** Coordination pillar. Balanced min-cut on coupling graph. Contract Composition Theorem. Conway's Law as graph containment.

**RAPID inspiration:** Sets, waves, jobs. DAG.json. CONTRACT.json. discuss-set -> plan-set -> execute-set pipeline.

### 2.1 Planning Pipeline (3-stage, from RAPID)

```
Stage 1: RESEARCH
  Input:  Task description, codebase context
  Agent:  research-agent (read-only, web search enabled)
  Output: RESEARCH.md -- tech options, pitfalls, existing patterns
  
Stage 2: PLANNING  
  Input:  RESEARCH.md, codebase context, CONTRACT.json
  Agent:  planner-agent
  Output: Per-wave PLAN.md files with:
          - Task breakdown (atomic units, one commit each)
          - File assignments (exclusive ownership per task)
          - Acceptance criteria (testable, not vague)
          - Dependency ordering
          
Stage 3: PLAN VERIFICATION
  Input:  PLAN.md files, RESEARCH.md, original task
  Agent:  plan-verifier-agent (read-only)
  Output: PLAN-CHECK.md -- goal-backward analysis:
          - Does the plan achieve the stated goal?
          - Are all acceptance criteria testable?
          - Are file assignments conflict-free?
          - Are dependencies correctly ordered?
```

### 2.2 Task Graph (DAG) for Multi-Agent Work

From RAPID's DAGv3 schema + the paper's coupling graph formalization:

```json
// .planning/DAG.json
{
  "version": 3,
  "nodes": [
    {"id": "auth-system", "name": "Authentication", "foundation": true},
    {"id": "api-gateway", "name": "API Gateway", "depends": ["auth-system"]},
    {"id": "user-dashboard", "name": "Dashboard", "depends": ["api-gateway"]}
  ],
  "edges": [
    {"from": "api-gateway", "to": "auth-system", "type": "DEPENDS_ON"},
    {"from": "user-dashboard", "to": "api-gateway", "type": "DEPENDS_ON"}
  ],
  "groups": [
    {"id": "backend", "sets": ["auth-system", "api-gateway"]},
    {"id": "frontend", "sets": ["user-dashboard"]}
  ]
}
```

**Decomposition algorithm:** The paper's balanced min-cut on the coupling graph, implemented via METIS or spectral partitioning. Practically: analyze the codebase's import/dependency graph, partition files into sets that minimize cross-set edges, assign each set to an agent.

### 2.3 Assume-Guarantee Contracts (from paper Theorem 5.5 + RAPID)

```json
// .planning/sets/auth-system/CONTRACT.json
{
  "setId": "auth-system",
  "assumptions": [
    "No other agent modifies files in src/auth/**",
    "Database schema for users table is stable",
    "JWT_SECRET environment variable is available"
  ],
  "guarantees": [
    "Exports: authenticate(user, pass) => Promise<Token>",
    "Exports: validateToken(token) => Promise<User>",
    "All modifications compile and pass auth tests",
    "Interface signatures preserved"
  ],
  "fileOwnership": {
    "exclusive": ["src/auth/**", "tests/auth/**"],
    "readOnly": ["src/types/user.ts", "src/db/schema.ts"]
  }
}
```

**Enforcement:** Contracts validated (1) after planning, (2) before execution, (3) before merge. Violations block the pipeline.

## Pillar 3: Reliability & Verification

**Paper grounding:** Compound Error Sensitivity (elasticity = n). Geometric Diminishing Returns. Structural Enforcement Boundary. Circular Validation Bias.

**RAPID inspiration:** Adversarial review cycles (hunter-advocate-judge). Four-layer verification. Scoped review by concern.

### 3.1 Four-Layer Verification Architecture

From the paper's efficiency ordering + RAPID's review pipeline:

```
Layer 1: STRUCTURAL GATES (cost: ~$0.50/PR, latency: 2-10s)
  - Type checking (tsc --noEmit)
  - Linting (eslint, clippy, ruff)
  - Schema validation (CONTRACT.json compliance)
  - File ownership enforcement (deny-list violations)
  - Import restrictions (architectural boundary checks)
  - Blueprint fitness functions (CI-runnable architecture tests)
  Enforcement: STRUCTURAL (filesystem permissions, tool restrictions, CI gates)
  Detection rate: ~0.95 for decidable defects

Layer 2: DETERMINISTIC ANALYSIS (cost: ~$2/PR, latency: 10-60s)
  - Unit tests (generated + existing)
  - Integration tests (contract tests from CONTRACT.json)
  - Property-based tests (for data transformations)
  - Clone detection (tree-sitter suffix tree, flag 5+ line duplicates)
  - Dead code analysis (call graph reachability)
  Enforcement: STRUCTURAL (CI pipeline, test suite must pass)
  Detection rate: ~0.80

Layer 3: LLM-AS-JUDGE (cost: ~$8/PR, latency: 20-120s)
  - Adversarial bug hunt (RAPID's hunter-advocate-judge pattern)
  - Cross-model verification (different model family than producer)
  - Scope expansion detection (diff vs. task spec comparison)
  - Architecture erosion check (Blueprint's compliance audit)
  Enforcement: INSTRUCTIONAL (agent-based, probabilistic)
  Detection rate: ~0.70
  
  CRITICAL: Layer 3 must use a DIFFERENT model family than the code producer.
  Same-model judging has correlated blind spots (paper FKG inequality).
  
  CRITICAL: Quality gates must be OPAQUE to the producing agent.
  METR showed 43x reward-hacking when scoring functions are visible.
  Run Layer 3 out-of-band, after generation, with no feedback about which checks exist.

Layer 4: HUMAN REVIEW (cost: ~$80/PR, latency: 10-60 min)
  - Architectural fit assessment
  - Business logic correctness
  - Undecidable slop types (meaningless tests, boilerplate inflation, naming drift)
  - Strategic alignment
  Enforcement: STRUCTURAL (merge requires human approval for high-risk changes)
  Detection rate: ~0.90
```

**Adaptive verification intensity:** From the paper's risk-based switching:
- **Low risk** (formatting, docs, well-tested patterns): Layers 1-2 only
- **Medium risk** (feature code, refactoring): Layers 1-3
- **High risk** (security-critical, cross-module, novel logic): All 4 layers

### 3.2 Adversarial Review Cycle (from RAPID)

The paper's Structural Separation Theorem + RAPID's hunter-advocate-judge:

```
Cycle 1 (broad scope):
  For each concern group (parallel):
    -> bug-hunter agent: find bugs, logic errors, edge cases
    -> devils-advocate agent: challenge findings, produce counter-evidence
    -> judge agent: rule ACCEPTED / DISMISSED / DEFERRED
    -> bugfix agent: apply fixes for accepted bugs (atomic commits)
    
Cycle 2-3 (narrowed scope, modified files only):
    -> Repeat on files touched by bugfix
    -> Prevents scope creep while catching regression
    
Max 3 cycles (paper's Geometric Diminishing Returns: 96.5% by round 3)
```

### 3.3 Structural Enforcement Boundary

From the paper's Theorem 4.5 + RAPID's enforcement:

| Invariant Type | Enforcement | Mechanism |
|----------------|-------------|-----------|
| File ownership | Structural | CONTRACT.json + deny-list in scoped CLAUDE.md |
| Type safety | Structural | Compiler (tsc, rustc, go build) |
| Test passage | Structural | CI gate (must pass to merge) |
| Import boundaries | Structural | Linter rules (eslint-plugin-boundaries, deptry) |
| Secret exclusion | Structural | .gitignore + pre-commit hook |
| Naming conventions | Instructional | CLAUDE.md rules (acceptable for subjective) |
| Code style | Instructional | CLAUDE.md rules (bounded by Layer 1 linter) |

**Decision rule (paper Theorem 4.5):** If the cost of a single violation exceeds `(c_structural - c_prompt) / epsilon`, enforce structurally. At epsilon = 0.23 (AgentSpec data), this means: any invariant where a single violation costs more than ~39x the prompt engineering cost should be structural.

### 3.4 Verification Checkpoints

From the paper's Young-Daly analog (Theorem 4.3):

For a typical 20-step pipeline with p = 0.95: **verify every 2-5 steps.**

Concretely: verify at wave boundaries (RAPID pattern), not at every atomic task. Three verification rounds capture 96.5% of detectable errors; the fourth faces the pesticide paradox.

## Pillar 4: Coordination & Multi-Agent

**Paper grounding:** Extended Amdahl's Law (n* = 1/sqrt(delta_a)). Quality-Adjusted Speedup. Capability Saturation Crossover. Write-skew prevention.

**RAPID inspiration:** Worktree isolation, DAG-ordered merge, 5-level conflict detection, 4-tier resolution cascade.

### 4.1 Optimal Agent Count

From the paper's Extended Amdahl's Law:

```
n* = 1 / sqrt(delta_a)

At delta_a = 0.05 (typical):  n* = 4-5 agents
At delta_a = 0.03 (good):     n* = 5-6 agents  
At delta_a = 0.10 (poor):     n* = 3 agents
```

**Practical rule:** Start with 3-5 agents. Measure QAS (Quality-Adjusted Speedup). If QAS < 1, you have too many agents. Scale DOWN as model capability improves.

### 4.2 Isolation Architecture (from RAPID)

```
project/
  .harness-worktrees/
    auth-system/        # git worktree for set 1 (rapid/{set-name} branch)
    api-gateway/        # git worktree for set 2
    user-dashboard/     # git worktree for set 3
    
  .planning/
    STATE.json          # Global state (atomic writes, lock-protected)
    DAG.json            # Dependency graph (topological ordering)
    CONTRACT.json       # Global interface contracts
    sets/
      auth-system/
        CONTRACT.json   # Set-specific contract
        PLAN.md         # Execution plan
        WAVE-COMPLETE.md # Progress markers
```

**Concurrency guarantees (mapped to database isolation, paper Table 4):**

| Isolation Level | Agent Mechanism | Prevents |
|-----------------|-----------------|----------|
| Snapshot | Git worktrees (frozen at dispatch) | Dirty reads, non-repeatable reads, phantoms |
| + Contracts | CONTRACT.json file ownership | Write-write conflicts |
| + Interface preservation | Signature checks before merge | API conflicts |
| Remaining risk | Write skew (semantic conflicts) | Detected by Layer 3 (LLM-as-Judge) at merge |

### 4.3 Merge Strategy (from RAPID's 5-level detection)

```
Step 1: Fast-path check
  git merge-tree --write-tree (exit 0 = clean merge, skip agents)

Step 2: 5-level conflict detection
  L1 Textual:    git merge (line-level)
  L2 Structural: AST differencing (GumTree/tree-sitter)
  L3 Dependency: Package resolver + compiler
  L4 API:        Interface signature comparison (from CONTRACT.json)
  L5 Semantic:   LLM agent analysis (compositional verification)

Step 3: 4-tier resolution cascade
  T1 (confidence > 0.9):  Auto-resolve, no review
  T2 (0.7-0.9):           Auto-resolve, flagged for human review
  T3 (0.3-0.7):           Delegate to conflict-resolver agent
  T4 (< 0.3):             Escalate to developer
  
  API signature conflicts: always T4 (too dangerous to auto-resolve)

Step 4: Merge ordering
  Topological sort on DAG.json -- dependencies merge first
  Each merge sees results of all prior merges
  Contract validation after each merge
```

## Pillar 5: Temporal & Execution

**Paper grounding:** VIH (Verified Iterations per Hour). Speculation Ratio Test. Context Fidelity Decay. Cache EOQ.

**RAPID inspiration:** Wave-sequential execution, crash recovery via markers, artifact-based re-entry.

### 5.1 Execution Pipeline (from RAPID)

```
For each wave (sequential within set):
  1. Load wave PLAN.md
  2. Check WAVE-COMPLETE.md markers (skip completed waves)
  3. Check git log for committed tasks (resume from last commit)
  4. Spawn executor agent with fresh context:
     - Scoped CLAUDE.md
     - PLAN.md (what to do)
     - CONTRACT.json (interfaces to preserve)
     - Reuse map (what already exists)
  5. Executor implements tasks:
     - One atomic commit per task
     - Commit message references task ID
  6. Write WAVE-COMPLETE.md marker
  
After all waves:
  7. Spawn verifier agent (lean check: do changes match plan?)
  8. Transition set to 'complete'
```

### 5.2 Crash Recovery (from RAPID)

The harness must be **fully recoverable from disk artifacts:**

```
Recovery algorithm:
  1. Read STATE.json (which sets exist, their status)
  2. For each in-progress set:
     a. Read PLAN.md files (expected waves)
     b. Scan WAVE-COMPLETE.md markers (completed waves)
     c. Scan git log (completed tasks within current wave)
     d. Resume from first incomplete task in first incomplete wave
  3. No conversation state needed (RAPID's /clear resilience)
```

### 5.3 Speculation (Conservative, Depth 1 Only)

From the paper's Speculation Ratio Test: speculate iff p/q > R/B.

```
Practical rule:
  - Speculate depth 1 only (begin next wave while verifying current)
  - Only when per-wave success probability > 0.85
  - Rollback cost (discard speculative work) must be < 2x benefit (time saved)
  - Never speculate on security-critical or cross-module changes
```

### 5.4 Context Freshness Management

From the paper's exponential staleness decay + RAPID's fresh context per agent:

```
Rules:
  1. Every agent invocation: fresh context (no accumulated state)
  2. Session checkpoint: 35 min or 50K tokens, whichever first
  3. Cache strategy: KV-cache for static prefixes (project rules, architecture)
     but regenerate task-specific context fresh each time
  4. Optimal refresh interval (paper's Cache EOQ):
     T* = sqrt(2R / (lambda * alpha * E_stale))
     For typical harness: refresh architectural context every 2-4 hours
```

## Pillar 6: Quality Defense

**Paper grounding:** 18 slop types in 3 detectability classes. Accretion Category. Three generative factors. Cost-of-quality model.

### 6.1 Slop Detection by Detectability Class

```
PRACTICALLY DECIDABLE (7 types) -- automated, Layer 1-2:
  Hallucinated imports     -> lockfile resolution
  Placeholder/stub code    -> AST pattern matching (pass, ..., NotImplementedError)
  Duplicate logic          -> tree-sitter clone detection (5+ line threshold)
  Dead code                -> call graph reachability
  Lint suppressions        -> grep for suppress/ignore/noqa patterns
  Cross-language contamination -> language-specific syntax checking
  Outdated APIs            -> deprecation database lookup

PARTIALLY DETECTABLE (7 types) -- LLM + heuristic, Layer 2-3:
  Security vulnerabilities -> SAST tools + LLM review (cross-model)
  Happy-path error handling -> exception path analysis + LLM
  Data model mismatches    -> schema comparison + LLM
  Over-engineering         -> complexity metrics + LLM judgment
  Architectural erosion    -> Blueprint compliance audit
  Silent scope expansion   -> diff vs. task spec comparison
  God functions            -> cyclomatic complexity + line count thresholds

RELIABLY UNDETECTABLE (4 types) -- aggregate monitoring only:
  Meaningless tests        -> test mutation score (if < 0.3, flag)
  Boilerplate inflation    -> lines per function point trend
  Redundant comments       -> comment-to-code ratio trend
  Naming/convention drift  -> consistency metrics over time
```

### 6.2 Accretion Monitoring (Aggregate, Not Per-Change)

From the paper's Compound Degradation theorem + Refactoring Ratio Threshold:

```
Monitor these metrics over time (statistical process control):
  - Duplication rate (target: < 12%, alarm at 15%)
  - Refactoring ratio (target: >= 20% of changes, alarm at < 10%)
  - Clone frequency (5+ line blocks, trend)
  - Codebase entropy H(C) = (1/n) * sum(log2(|mu(f_i)|))
  - Lines per function point (trend)
  - Dependency fan-out (mean, trend)
  
Trigger architectural review when:
  - Refactoring ratio drops below equilibrium (paper's 2.5x violation threshold)
  - Duplication rate increases > 2x over 3 months
  - Codebase entropy growth rate exceeds historical baseline by > 1 std dev
```

### 6.3 Cost-Aware Quality Targeting

From the paper's Optimal Quality Level theorem:

```
q* = (1/beta) * ln(c_F * lambda_0 * beta / (c_P + c_A))

Practical quality tiers:
  Security-critical production:  q* ~ 1.0   -> All 4 layers, full adversarial review
  Standard production code:      q* ~ 0.85  -> Layers 1-3, 2 review cycles
  Internal tools:                q* ~ 0.70  -> Layers 1-2 only
  Prototypes/experiments:        q* ~ 0.30  -> Layer 1 only (linting + types)
```

## Pillar 7: Governance (from Blueprint)

**Paper grounding:** Governance Rate-Stability Principle. Governance Bifurcation. Ratchet Lattice with controlled relaxation. Decision Survival Analysis.

**Blueprint inspiration:** ADR lifecycle, evidence tracking, fitness functions, drift detection, cascade control.

### 7.1 Three-Loop Cascade Governance (from paper + Blueprint)

```
INNER LOOP (per-generation, seconds):
  - Blueprint pre-commit guard (/blueprint:guard)
  - Structural gates (Layer 1 verification)
  - File ownership enforcement
  - Import boundary checks
  Bandwidth: high. Sampling: every code generation.

MIDDLE LOOP (per-phase, minutes-to-hours):
  - Blueprint compliance audit (/blueprint:audit)
  - Blueprint reflexion model (/blueprint:reflect)
  - Contract verification
  - Adversarial review cycles (RAPID's bug-hunt)
  Bandwidth: moderate. Sampling: at wave/set boundaries.

OUTER LOOP (per-milestone, days-to-weeks):
  - Blueprint architecture evaluation (/blueprint:evaluate -- 5 parallel agents)
  - Blueprint drift detection (/blueprint:drift)
  - Blueprint decision debt check (/blueprint:debt)
  - Strategic alignment review (Wardley map, tech radar)
  - ATAM tradeoff analysis (/blueprint:tradeoff)
  Bandwidth: low. Sampling: milestone boundaries.
  
BANDWIDTH SEPARATION: Each loop differs by >= 3:1 in sampling rate (paper's cascade stability condition).
```

### 7.2 ADR Lifecycle (from Blueprint)

```
States: Proposed -> Accepted -> Deprecated/Superseded
                 -> Rejected
                 -> Deferred (with trigger condition)

Creation: /blueprint:new [--research]
  1. Interview proposer about the decision
  2. Optional: spawn researcher agent for evidence gathering
  3. Draft ADR with structured template
  4. Run impact analysis (cross-ADR conflicts)
  5. Index in README.md + update relationships.toml

Review: /blueprint:review N (devil's advocate)
  Challenge across 5 dimensions:
  1. Assumptions audit
  2. Alternatives gap
  3. Consequence completeness
  4. Risk underestimation
  5. Reversibility assessment

Acceptance: /blueprint:transition accept N
  - Validates prerequisites (review completed)
  - Updates evidence tracking
  - Generates fitness function (if testable invariant)
  - Commits to git

Evidence tracking: /blueprint:evidence
  - L0 (unverified): AI-generated, expires 60 days
  - L1 (logically consistent): sourced, expires 180 days
  - L2 (empirically validated): tested in project, longest validity
  - Conservative aggregation: decision confidence = min(evidence levels)
```

### 7.3 Decision Survival & Relaxation

From the paper's survival analysis + Blueprint's debt tracking:

```
Decision half-lives (from paper):
  UI/frontend decisions:    ~1.2 years
  API contracts:            ~2.5 years
  Data model decisions:     ~4.3 years
  Core architecture:        ~7+ years

Governance actions:
  - Track decision age alongside content (/blueprint:debt)
  - Proactively surface decisions approaching half-life
  - Evidence expiry triggers review, not automatic deprecation
  - Controlled relaxation: remove expired rules, re-derive consequences
  - Ossification prevention: the ratchet must have a release mechanism
```

### 7.4 Rate-Stability Monitoring

From the paper's Governance Rate-Stability Principle:

```
Monitor: R_drift / C_gov ratio

R_drift (drift rate): ADR violations per month + layer boundary violations + 
                      convention violations in new code
                      
C_gov (governance throughput): PRs reviewed per month * review depth +
                               ADR update rate + architectural review frequency +
                               automated gate coverage fraction

ALARM when R_drift / C_gov > 0.8 (approaching threshold)
CRITICAL when R_drift / C_gov > 1.0 (coherence collapse regime)

Response: increase automated governance (inner loop) to match velocity
```

## Pillar 8: Cost Optimization (Reviewer Gap #1)

**Not in the paper.** R3: "Cost is the binding constraint in practice."

### 8.1 Token Budget Model

```
Per-task cost model:
  C_task = sum over calls:
    (input_tokens * price_in + output_tokens * price_out) * (1 - cache_discount)

Budget allocation:
  Planning:     10-15% of budget (research + plan + verify)
  Execution:    50-60% of budget (the actual work)
  Verification: 20-25% of budget (review cycles)
  Governance:   5-10% of budget (compliance, drift checks)
  
Hard constraints:
  - Per-task budget cap (configurable, default $50)
  - Per-call context budget (never exceed 0.40W)
  - Escalation: if budget exhausted before task complete, checkpoint and escalate
```

### 8.2 Model Routing by Task Type (connects to Pillar 10)

```
Task classification -> model selection:
  Planning/research:     Large model (Opus-class)    -- quality critical
  Code execution:        Large model (Opus-class)    -- quality critical
  Layer 1-2 verification: No LLM needed              -- deterministic tools
  Layer 3 verification:  Medium model (Sonnet-class) -- cross-model diversity
  Bug hunting:           Medium model (Sonnet-class) -- volume over depth
  Documentation:         Small model (Haiku-class)   -- speed, low stakes
```

### 8.3 Cost-Quality Pareto Optimization

From the paper's VIH tangency condition:

```
Optimize: VIH = lambda_raw * p_verify

At the optimum, elasticity of quality w.r.t. speed = -1.
A 1% increase in raw speed causes exactly 1% decrease in verification rate.

Practical: mix "fast mode" (minimal verification) and "governed mode" (full verification):
  - 70% of tasks in fast mode (boilerplate, well-understood)
  - 30% of tasks in governed mode (novel, security-critical, cross-module)
  - This convexifies the Pareto frontier (paper Theorem 6.8)
```

## Pillar 9: Human-in-the-Loop (Reviewer Gap #2)

**Not in the paper.** R3: "The dominant quality mechanism, treated as Layer 4 afterthought."

### 9.1 Human Interaction Points

```
MANDATORY human gates:
  1. Task specification approval (before planning begins)
  2. Plan review (before execution begins) -- can modify/reject
  3. Merge approval for high-risk changes
  4. Escalation response (when agent is blocked or budget exceeded)
  
OPTIONAL human gates (configurable):
  5. Mid-execution checkpoints (after each wave, for long tasks)
  6. Review cycle participation (human as Layer 4 reviewer)
  7. Architecture decision review (Blueprint's ADR acceptance)
  
NEVER block human on:
  8. Layer 1-2 verification (fully automated)
  9. Context generation (fully automated)
  10. State management (fully automated)
```

### 9.2 Bayesian Mode Selection (from paper Theorem 6.7)

```
Choose "governed" (human-reviewed) mode when:
  P(governed needed | features) > c_GF / (c_FG + c_GF)

Since c_FG >> c_GF (cost of missing a needed review >> cost of unnecessary review):
  Threshold is low: ~0.05-0.10
  
Meaning: choose governed mode even when probability of needing it is only 5-10%.

Features for classification:
  - Security-critical files touched
  - Cross-module changes
  - Novel logic (high abstraction gap estimate)
  - External API changes
  - Database migration
```

### 9.3 Triage, Not Exhaustive Review

From the paper's Detection Ceiling + throughput mismatch:

```
Human review should be DIRECTED by automated layers:
  1. Layers 1-3 filter the stream (catch 90%+ of detectable defects)
  2. Human reviews only what passes automated checks
  3. Human focuses on undecidable types: architectural fit, business logic, naming
  4. Time budget: 10-15 min per PR, not 60 min
  
Dodge-Romig adaptive inspection:
  - Tighten review for agents with recent quality issues
  - Relax review for agents with consistent quality track record
  - Sample-based: review 100% of high-risk, 30% of medium-risk, 5% of low-risk
```

### 10.2 Cross-Model Verification

From the paper's FKG inequality + Diversity Gain:

```
CRITICAL RULE: The verification model must be from a DIFFERENT family than the producer.

If producer = Claude Opus:
  Layer 3 judge = GPT-4o or Gemini Pro (cross-family)
  
Why: Same-model judging has correlated blind spots.
P(both miss defect) >= P(producer misses) * P(judge misses)
Independence assumption UNDERESTIMATES escape probability.

Even a weaker independent detector outperforms a stronger correlated one
in marginal DRE improvement.
```

## Key Design Principles (Prioritized)

From the paper's 35 principles, RAPID's patterns, and Blueprint's governance, the 15 highest-leverage principles for implementation:

1. **Enforce structurally what must hold invariantly.** Filesystem permissions, not prompts.
2. **Budget context, do not maximize it.** 0.15W-0.40W, not the full window.
3. **Fresh context per agent.** No accumulated state. Checkpoint and restart.
4. **Fix the weakest link first.** Usually problem framing (step 1), not execution.
5. **Three verification rounds, then stop.** Diminishing returns are geometric.
6. **The verifier must be structurally read-only.** Tool permissions, not instructions.
7. **Separate code authorship from test authorship.** Cross-model, cross-family.
8. **Quality gates must be opaque to the producer.** 43x reward-hacking otherwise.
9. **Decompose along low-coupling boundaries.** Min-cut on dependency graph.
10. **Contracts reduce conflict scaling from O(k^2) to O(k).** File ownership is mandatory.
11. **Measure QAS, not raw throughput.** If QAS < 1, reduce agents, don't add more.
12. **Maintain the refactoring ratio.** >= 20% of changes. Monitor, alarm, intervene.
13. **Govern at three granularities.** Per-generation, per-phase, per-milestone.
14. **Track decision age, not just content.** Evidence expires. Proactively surface.
15. **Accept what you cannot detect.** Undecidable types get aggregate monitoring, not per-instance gates.
