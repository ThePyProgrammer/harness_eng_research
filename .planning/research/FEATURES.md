# Feature Research

**Domain:** Static academic book/wiki website for a Markdown/LaTeX research corpus
**Researched:** 2026-05-13
**Confidence:** MEDIUM

## Feature Landscape

### Table Stakes (Users Expect These)

Features users assume exist. Missing these = product feels incomplete.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Full corpus coverage: umbrella framework plus all twelve pillars | The site's promise is a unified research corpus, not a sample chapter. Researchers will leave if key pillars are absent or visibly incomplete. | MEDIUM | Must include `science/paper/` and every `pillars/*/paper/` area in v1, even if some supporting notes are deferred. |
| Book-style chapter navigation | Academic readers need a stable reading order, next/previous links, table of contents, and clear hierarchy. | LOW | Include overview, umbrella framework, pillar chapters, glossary, bibliography, and reading paths. |
| Pillar landing pages | Each pillar needs a compact conceptual entry point before diving into formal statements. | LOW | Use the existing pillar list and focus summaries as the starting spine. Each page should answer: problem, core model, definitions, theorems, implications, related pillars. |
| Formal definition blocks | Researchers reading formal work expect definitions to be findable, addressable, and visually distinct. | MEDIUM | Render definitions with stable anchors, labels, source links, notation, assumptions, and related concepts. |
| Theorem/proposition/lemma blocks | Formal claims must not be buried in prose. | MEDIUM | Use consistent callouts for theorem-like environments with numbering, statement, assumptions, proof sketch or source pointer, and related derivations. |
| Derivation pages or expandable derivation sections | The project explicitly values mathematical rigor; summaries without derivations are too shallow. | HIGH | Curate derivations from canonical LaTeX rather than attempting full automatic semantic extraction in v1. Include enough intermediate steps for auditability. |
| Citation rendering and bibliography pages | Academic readers expect citations, bibliography entries, and backlinks from citation to use sites. | MEDIUM | Preserve citation keys where useful, render readable references, and link to source `.bib` files or paper PDFs. |
| Source trails to canonical files | The website must not become an untraceable fork of the research corpus. | MEDIUM | Each page and formal block should link back to canonical `.tex`, `.bib`, PDF, and relevant notes/research files. |
| Local static search | Researchers need to find definitions, theorem statements, citations, glossary terms, and pillar concepts quickly. | MEDIUM | Search index should distinguish content types: page, definition, theorem, citation, glossary entry, pillar. No hosted search service for v1. |
| Cross-linking between concepts, definitions, theorems, and pillars | Wiki-style exploration is core to understanding cross-pillar relationships. | HIGH | Start curated. Do not wait for full ontology automation. Every pillar should expose outgoing and incoming concept relationships. |
| Glossary / concept index | A formal corpus needs a place where recurring terms and notation are normalized. | MEDIUM | Include aliases, pillar ownership, definition source, related terms, and disambiguation notes. |
| Reading paths | Different researchers arrive with different concerns: harness building, scaling, cost/latency, production hardening, code degradation. | LOW | Use the existing README reading paths as launch paths. Each path should be a sequence with rationale. |
| Responsive, readable academic layout | Long mathematical pages must be comfortable to read on laptop and tablet widths. | MEDIUM | Prioritize typography, line length, sidebar behavior, equation overflow, printability, and dark/light contrast. |
| Stable deep links | Researchers cite, share, and revisit exact definitions and theorem statements. | LOW | Use durable slugs and anchors; avoid autogenerated IDs that change when headings move. |
| PDF access alongside web chapters | The canonical papers already exist as PDFs; many academic readers will want the original. | LOW | Every pillar and umbrella page should link to the canonical PDF prominently. |
| Archive/provenance distinction | The repo contains archives that are preserved but non-canonical. Researchers need clarity on what is authoritative. | LOW | Pages should mark canonical, supporting, and archived material distinctly. Archive links should be provenance-only unless explicitly discussed. |

### Differentiators (Competitive Advantage)

Features that set the product apart. Not required, but valuable.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Cross-pillar concept graph | Turns the site from a book into a research map, showing how abstraction, information, reliability, governance, economics, security, and other pillars depend on one another. | HIGH | Curated graph metadata can launch before advanced visualization. Graph should support concept-to-concept and theorem-to-pillar relationships. |
| Formal object registry | Makes every definition, theorem, lemma, proposition, assumption, equation, and citation addressable as a first-class object. | HIGH | Enables search filters, backlinks, graph links, glossary, and source trails. Best implemented as structured frontmatter/data adjacent to curated pages. |
| Claim-to-source traceability | Builds trust by showing exactly which canonical paper section supports each explanation or formal claim. | HIGH | Distinguish direct quotation, paraphrase, interpretation, and synthesis. This is more valuable than decorative polish. |
| Derivation walkthrough mode | Helps researchers audit equations without losing the narrative. | HIGH | Use collapsible steps, assumptions, notation reminders, and links back to theorem statements. Defer interactive symbolic tooling. |
| Cross-pillar comparison pages | Helps readers see repeated patterns across pillars, e.g. capacity constraints, degradation dynamics, verification scheduling, governance ratchets. | MEDIUM | These synthesis pages are useful after the first pass of pillar pages and glossary exists. |
| Reading-path progress maps | Gives researchers a way to traverse the corpus by intent rather than folder structure. | MEDIUM | Keep static and local. No accounts; use visual maps and ordered pages, not stored progress. |
| Notation index | Academic readers often struggle less with prose than with notation drift across papers. | MEDIUM | Record symbols, meanings, owning pillar, overloaded meanings, and first-use locations. |
| Citation influence/backlink view | Shows where references are used across the corpus and which ideas they support. | MEDIUM | Useful once citation extraction/curation is stable. Keep it static. |
| Concept relationship pages | For important concepts, create pages that aggregate definitions, related theorem statements, pillar occurrences, and citations. | HIGH | Strong differentiator for research usability. Depends on glossary and formal object registry. |
| Printable / citation-friendly pages | Researchers may want to cite or annotate chapters. | MEDIUM | Provide clean print CSS, stable page metadata, canonical URL, last-updated timestamp, and source links. |
| Research status badges | Makes epistemic status visible: canonical, supporting note, synthesis, review, archived, speculative. | LOW | Particularly important in a brownfield corpus with papers, notes, research artifacts, reviews, and archives. |

### Anti-Features (Commonly Requested, Often Problematic)

Features that seem good but create problems.

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Dynamic user accounts, comments, or collaborative editing | Looks like a community wiki and enables reader discussion. | Adds moderation, auth, spam, privacy, persistence, and operational burden. Violates v1 static publication scope. | Keep the site static. Use repository issues/discussions separately if feedback is needed later. |
| Server-side CMS or database | Seems easier for editing pages and relationships. | The corpus already lives in git; a CMS creates a second source of truth and migration burden. | Store curated pages and graph metadata in version-controlled files. Build static output. |
| Full automatic LaTeX semantic extraction as the only pipeline | Promises complete coverage with less manual work. | LaTeX papers are not a clean semantic database; automatic extraction will likely produce brittle, unreadable, or wrong pages. | Use curated hybrid content with selective helper scripts for citations, headings, labels, and source links. |
| Exact visual clone of another research lab's site | Gives a quick aesthetic target. | Creates brand-copy risk and weak identity. Also distracts from corpus-specific needs like theorem navigation and source trails. | Build an original editorial/book identity optimized for formal reading. |
| Live interactive theorem proving or symbolic derivation checking | Sounds rigorous and impressive. | Massive scope increase and likely unrelated to v1 reader value unless the corpus is already encoded in a proof assistant. | Provide transparent derivation walkthroughs and source-linked assumptions. |
| AI-generated explanations without source gating | Speeds up page creation. | High risk of hallucinated definitions, theorem drift, and subtle mathematical errors. | Require every explanation to cite canonical source sections or be marked as interpretation/synthesis. |
| One polished pillar demo instead of full corpus coverage | Easier to ship something beautiful quickly. | Fails the core value: cross-pillar framework and wiki coverage. Researchers need the whole map. | Launch all pillars with consistent minimum depth, then deepen high-value pages. |
| Treating archived material as active source content | Archives may contain useful drafts or older explanations. | Blurs authority and may resurrect obsolete claims. | Link archives only as provenance; default source hierarchy is canonical paper, then notes/research/reviews. |
| Overbuilt interactive graph as the primary navigation | Graph visualizations look impressive. | Dense graphs can become unusable and slow; they do not replace chapter navigation or search. | Use graph as secondary exploration with curated relationship pages and filtered views. |
| Hosted search service | Easy relevance and indexing. | Unnecessary for a static corpus, adds vendor dependency and possibly privacy/availability concerns. | Use local static search index generated at build time. |
| Reader personalization requiring persistence | Could offer saved paths and progress. | Requires accounts or browser storage complexity and is not necessary for research publication v1. | Provide deterministic reading paths and anchorable pages. Optional local-only UI state can come later. |

### Dependency Notes

- **Canonical source inventory precedes source trails:** the site cannot link claims back to authoritative material until canonical `.tex`, `.bib`, PDFs, notes, reviews, and archive boundaries are inventoried.
- **Stable deep links are foundational:** search, glossary, theorem references, concept pages, and graph edges all depend on durable anchors.
- **Formal object registry is the keystone differentiator:** it is not mandatory to expose the registry as a public feature immediately, but implementing the content model early prevents rewrites later.
- **Cross-pillar graph should come after curated relationships:** a graph without accurate concepts, anchors, and relationship types becomes decorative noise.
- **Derivation walkthroughs depend on theorem structure:** derivations should hang off claims, assumptions, and notation, not exist as isolated math dumps.
- **Local search depends on metadata quality:** a generic page search is table stakes, but research-grade search requires indexing formal object types separately.
- **Anti-features conflict with source discipline:** CMS, dynamic collaboration, AI-generated ungated explanations, and archive-as-source all weaken trust in the corpus.

## MVP Definition

### Launch With (v1)

Minimum viable product — what's needed to validate the concept.

- [ ] Full corpus coverage: umbrella framework plus all twelve pillars — essential because a cross-pillar corpus site that omits pillars breaks the product promise.
- [ ] Book-style chapter navigation — essential because researchers need a sane linear path through a large formal corpus.
- [ ] Pillar landing pages — essential because each pillar needs a readable entry point before formal detail.
- [ ] Formal definition blocks — essential because definitions are core research objects, not decorative callouts.
- [ ] Theorem/proposition/lemma blocks — essential because formal claims need consistent treatment and anchors.
- [ ] Citation rendering and bibliography pages — essential because this is an academic site.
- [ ] Source trails to canonical files — essential because the website must remain grounded in the corpus sources.
- [ ] Stable deep links — essential because formal objects need to be cited and cross-linked.
- [ ] Local static search — essential because the corpus is too broad to browse manually every time.
- [ ] Glossary / concept index — essential because cross-pillar terminology must be normalized.
- [ ] Reading paths — essential because the README already defines intent-based paths users will expect on the site.
- [ ] Responsive, readable academic layout — essential because long-form formal reading is the primary interaction.
- [ ] Archive/provenance distinction — essential because the repository contains preserved non-canonical material.

### Add After Validation (v1.x)

Features to add once core is working.

- [ ] Derivation pages or expandable derivation sections — add once theorem and source-link conventions are stable; high value but costly.
- [ ] Cross-linking between concepts, definitions, theorems, and pillars — start in v1 where obvious, expand systematically in v1.x.
- [ ] Formal object registry — implement minimal metadata early, expose richer registry once object taxonomy stabilizes.
- [ ] Claim-to-source traceability — deepen from page-level source links to claim/block-level source links after initial curation.
- [ ] Notation index — add when notation drift or overload is visible across first-pass pillar pages.
- [ ] Printable / citation-friendly pages — add after page metadata and canonical URL patterns are stable.
- [ ] Research status badges — add when readers need clearer distinction between canonical, synthesis, review, and archive sources.

### Future Consideration (v2+)

Features to defer until product-market fit is established.

- [ ] Cross-pillar concept graph visualization — valuable, but only after relationship data is accurate enough not to mislead.
- [ ] Concept relationship pages — high-value research affordance, but depends on mature glossary, formal objects, and backlinks.
- [ ] Cross-pillar comparison pages — defer until all pillars have enough consistent structure to compare honestly.
- [ ] Citation influence/backlink view — defer until citation parsing and source usage are reliable.
- [ ] Reading-path progress maps — nice-to-have; deterministic reading paths matter more than progress UI.
- [ ] Interactive derivation aids — defer unless derivation walkthroughs prove insufficient.

## Competitor Feature Analysis

| Feature | Academic book sites | Wiki / documentation sites | Our Approach |
|---------|---------------------|----------------------------|--------------|
| Linear reading order | Strong: chapters, sections, table of contents, next/previous navigation. | Often weaker: page graph and search dominate. | Use book navigation as the default spine across overview, umbrella, pillars, glossary, bibliography, and reading paths. |
| Formal math presentation | Strong in papers/books, variable on websites. | Often weak unless docs are math-specific. | Treat definitions, theorems, assumptions, derivations, notation, and citations as first-class content. |
| Cross-linking | Usually limited to references and section links. | Strong page-to-page linking, but often informal. | Combine wiki-style cross-links with academic source discipline and stable formal-object anchors. |
| Search | Common but often page-level. | Common and expected. | Provide local static search with filters for pages, definitions, theorems, citations, glossary entries, and pillars. |
| Source traceability | Papers have references but not always source-file traceability. | Docs may link to source, but not always claim-level. | Link every page, and eventually major formal blocks, back to canonical `.tex`, `.bib`, PDF, notes, or research files. |
| Concept graph | Rare in traditional academic books. | Sometimes present in knowledge bases, often noisy. | Use a curated graph as differentiator, not as a substitute for navigation. |
| Provenance/status markers | Usually implicit. | Often absent or ad hoc. | Explicitly mark canonical, supporting, synthesis, review, and archived material. |
