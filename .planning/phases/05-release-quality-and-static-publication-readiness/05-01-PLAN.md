<objective>
Create the first release-readiness vertical slice: a runnable publication gate that composes existing validators and reports the required unified pass/fail summary with grouped actionable diagnostics.

Purpose: Phase 5 needs a single publication decision point before adding new release gates, and this plan gives builders an immediate command that blocks on existing source-trail, archive, citation, formal registry, and discovery integrity.
Output: `bun run release` works from `site/`, preserves focused scripts, and exposes typed release diagnostics for later plans to extend.
</objective>

<phase_goal>
**As a** static site builder, **I want to** run a clean publication readiness command, **so that** I can know whether the academic book/wiki is safe to publish from checked source and generated static output.
</phase_goal>

<decision_traceability>
- D-01: This initial release-readiness slice starts the publication gate bar by composing existing source-trail, archive-exclusion, citation, formal-registry, discovery, and graph-target validators, with later Phase 5 gates represented as typed pending totals until final composition.

- D-04: This plan explicitly excludes advanced graph filtering, rich relationship pages, versioned releases, analytics, and automated provenance diff reports.
- D-10: Command location is centered under `site/`; implementation stays under `site/` and canonical `science/` / `pillars/` files remain read-only inputs.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Registry data -> release validator | Typed but untrusted source metadata, paths, anchors, and relation IDs enter publication decision logic. |
| CLI -> stdout/stderr | Release result crosses from tooling into human publication workflow. |
| Package scripts -> local shell | `bun run release` executes local TypeScript scripts from the checked site workspace. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01-01 | Tampering | `runReleaseReadiness` validator composition | mitigate | Import existing typed validators directly; preserve archive, path traversal, source trail, citation, and graph target failures as blocking diagnostics. |
| T-05-01-02 | Repudiation | release CLI output | mitigate | Include `gate`, `entryId`, `field`, `path`, `reason`, and `nextStep` for every failure so release decisions have attributable evidence. |
| T-05-01-03 | Information Disclosure | diagnostic paths | accept | Diagnostics expose repository-relative source paths already published as source trails; no secrets or external service tokens are introduced. |
| T-05-01-04 | Denial of Service | release orchestration | accept | Current gates are local static validators over bounded registries; no network or unbounded filesystem scan is added in this plan. |
| T-05-01-SC | Tampering | npm installs | mitigate | No new package installs; if execution discovers a required new npm package, stop and require package legitimacy review before modifying dependencies. |
</threat_model>
